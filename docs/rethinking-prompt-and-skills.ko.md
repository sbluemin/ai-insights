# 프롬프트와 스킬 다시 생각하기: 유효기간이 있는 런타임 컨텍스트

> **한 줄 요지** — 지침과 스킬은 설명서가 아니다. 다음 탐색 위치와 넘으면 안 되는 경계를 결정하는 **상시 로드 컨텍스트 라우터**이며, 그 안의 모든 조타(steering) 문장은 *"모델이 이걸 혼자 못한다"*는 가정에 건 베팅이다. 상시 주입·탐색·위반·재작업·유지보수의 총비용을 최소화하되, 그 베팅은 능력 기준선이 움직이면 **만료**되므로 쌓지 말고 재감사한다.

> English: [rethinking-prompt-and-skills.md](./rethinking-prompt-and-skills.md)

# 1부 — 애초에 무엇을 담는가

## 1. 지침의 역할은 두 가지면 충분하다

일반 문서는 필요할 때 찾아 읽지만, 상시 지침은 관련 스코프에 들어갈 때마다 비용을 낸다. 따라서 다음 두 역할만 맡긴다.

1. **탐색 공간 축소** — 어느 책임 영역·디렉터리로 가야 하는가.
2. **경계 보존** — 코드를 부분적으로 읽으면 놓치기 쉬운 소유권·의존 방향·신뢰·승인 불변식은 무엇인가.

기능 설명, 구현 목록, 작업 명령, 변경 이력까지 담으면 지침은 축소판 문서 포털이 된다. 그때부터 탐색을 돕기보다 오래된 사전지식(stale prior)을 반복 주입한다.

## 2. 위험도 기반 보존 게이트

문장은 상시 주입 비용보다 **미리 아는 기대편익**이 클 때 남긴다.

```text
기대편익 = 탐색 절감 + (발견 지연 가능성 × 위반 비용)
총비용   = 반복 주입 비용 + drift·유지보수 비용
```

| 축 | 확인할 질문 |
|---|---|
| **선행 필요성** | 작업이나 수정 전에 알아야 하는가 |
| **발견 지연** | 일반 탐색이 올바른 시점까지 이를 드러내지 못할 가능성이 큰가 |
| **위반 비용** | 놓치면 보안, 데이터, 배포, 승인, 소유권 오류가 커지는가 |
| **안정성과 재사용** | 구현이 변해도 유효하고 해당 스코프에서 반복되는가 |
| **대체 수단** | 자동화나 온디맨드 라우팅이 더 싸고 확실한가 |

모든 축을 같은 비중의 AND 조건으로 다루지 않는다. 드물게 발생해도 위반 비용이 매우 크거나 발견이 너무 늦는 불변식은 남길 수 있다.

계속 필요한 기계 규칙은 **먼저** lint·schema·generator·CI로 이전하고, 그 메커니즘이 위반을 저비용으로 차단한다는 증거가 생긴 뒤에만 지침에서 제거한다. 더 이상 유효하지 않은 규칙을 폐기하는 판단과, 유효한 규칙의 집행 위치를 옮기는 판단을 구분한다.

## 3. 설명이 아니라 제약을 남긴다

"현재 무엇이 어디에 있다"는 빨리 낡고, "무엇이 어디를 넘어가면 안 되고 어떤 사실은 코드 탐색 뒤에 발견하면 늦는가"는 오래 산다. 같은 구분이 불변식과 절차를 가른다 — **절차는 능력이 오를수록 빨리 낡고, 불변식은 낡지 않는다.**

| 지침에 남길 것 | 다른 SSoT로 보내거나 모델에 맡길 것 |
|---|---|
| owner / must-not-own | 현재 구현 책임과 source layout |
| 허용·금지된 의존 방향 | import와 dependency 목록 |
| trust / security / approval boundary | route·DTO·필드 목록 |
| 하나여야 하는 정책 owner | 현재 symbol·registry 내용 |
| authoring source와 generated output 경계 | 생성물 내용의 수동 복사 |
| 데이터 손실·배포를 막는 필수 gate | 전체 실행 명령 카탈로그 |
| 구현을 가로지르는 lifetime 의미 | 동작 절차와 장애 회고 |
| **무엇이 참이어야 하는가** — 불변식·수용 기준 | **어떻게 거기 도달하는가** — 단계 순서, 어떤 파일을 먼저 열지 |
| 비자명한 함정과 **그 이유** | 자명한 확인 절차의 나열 |
| 순서 자체가 안전 요건인 경우 | 순서가 편의일 뿐인 경우 |

트리거 + 행동 + **이유**로 적으면(→ [수확 방법론 §2③](./compounding-engineering-learning-harvest.ko.md)) 맥락이 바뀌었을 때 모델이 재판단할 수 있다. 이유 없는 단계 나열은 카고컬트를 만든다.

상세 정보의 거처 선택과 이전 원칙은 [정주·SSoT 방법론](./compounding-engineering-learning-harvest.ko.md)을 따른다. 같은 사실을 상시 지침과 상세 문서에 복사하지 않는다.

## 4. 색인은 탐색 공간만 줄인다

색인의 기본 해상도는 **디렉터리·패키지·도메인**이다. 목적은 정답 파일을 미리 알려주는 것이 아니라, 검색해야 할 영역을 빠르게 좁히는 것이다.

exhaustive 파일 색인은 검색 기능과 중복되고 구조 변경에 즉시 낡는다. 다만 유일한 정책 SSoT, composition root, 생성물 owner, 승인 manifest처럼 **안정적이고 놓쳤을 때 비용이 큰 파일**은 드문 landmark로 허용한다. 이는 목록이 아니라 잘못된 작성·탐색 시작점을 막는 경계다.

## 5. 계층형 컨텍스트는 지역화한다

조상 지침은 모든 자손 컨텍스트에 반복 합성된다. 긴 상위 지침은 모든 하위 작업에 붙는 세금이며, 가장 구체적인 leaf 지침이 들어갈 공간을 먼저 소모한다.

- 전역 지침에는 정체성과 전역 불변식만 둔다.
- 공유 규칙은 적용되는 **가장 낮은 공통 조상**에 한 번만 둔다.
- leaf는 부모를 재진술하지 않고 **로컬 차이(delta)**만 추가한다.
- 두 sibling에 같은 의미가 반복되면 공통 부모로 올린다.
- 특정 하위 영역의 예외를 편의상 전역 규칙으로 승격하지 않는다.
- 여러 하네스가 다른 지침 이름을 요구하면 사본 대신 하나의 SSoT를 참조한다.

문자 그대로 같은 문장보다 **의미 중복**을 경계한다. 표현이 달라도 같은 소유권·DI·공개 경계를 여러 계층에서 설명하면 비용과 drift는 그대로 늘어난다.

# 2부 — 담은 것이 왜 낡는가

## 6. 조타는 한 방향으로만 쌓인다 (래칫)

조타 문장은 대개 과거의 실패 1건에 대한 응답으로 추가된다. 그런데 **추가의 계기는 관측되지만 삭제의 계기는 관측되지 않는다.**

- 모델이 넘어서면 → 사건이 나고, 누군가 "앞으론 ~하지 마라" 한 줄을 박는다.
- 모델이 그 실수를 더 이상 하지 않게 되면 → **아무 일도 일어나지 않는다.** 알림도, 실패도 없다.

그래서 지침은 단방향 래칫처럼 길어진다. 낡음은 침묵으로 나타나므로, **삭제는 사건이 아니라 주기적 감사로만 일어난다.**

### 능력 기준선이 오르면 비용 구조가 뒤집힌다

| | 능력이 낮던 시점 | 능력이 오른 뒤 |
|---|---|---|
| 지배적 실패 | **과소 지시** — 빠뜨림, 검증 안 함, 엉뚱한 파일 | **과잉 지시** — 불필요한 열람·재실행, 범위 축소, 조기 중단 |
| 문장의 효과 | 실패를 막는다 | 이미 할 일을 **또 하게** 하거나, 할 일을 **막는다** |
| 비용의 가시성 | 높음(사건으로 드러남) | **낮음**(느려지고 덜 하는 것으로만 드러남) |

핵심은 새 비용이 *조용하다*는 점이다. 과잉 조타는 에러를 내지 않는다. 그저 매 작업을 조금씩 비싸게 만들고, 가끔 완주했어야 할 일을 도중에 세운다.

### 재감사 트리거

> 다음을 보면 → 지침·스킬 전면 재감사 → 왜냐면 능력 가정이 조용히 무효가 되어도 스스로 신호를 내지 않으니까.

- **모델 기준선 변경** — 교체·업그레이드·설정 변경. 가장 명확한 계기다.
- **같은 지침 아래 반복되는 잉여 행동** — 시키지 않아도 하는 일을 또 시키고 있다는 신호.
- **지침 길이의 단조 증가** — 최근 N개월간 추가만 있고 삭제가 없었다면 이미 늦었다.

## 7. 스킬 표면: 상시 비용은 본문이 아니라 트리거에 있다

스킬(절차 문서)은 두 부분으로 나뉘고, **비용을 내는 시점이 서로 다르다.**

| 부분 | 비용 시점 | 설계 목표 |
|---|---|---|
| **회수 트리거**(이름·설명) | **상시** — 카탈로그에 있는 한 계속 | 정확한 발동, 최소 분량 |
| **본문** | 발동 시에만 | 필요한 만큼만 펼쳐짐 |

### ① 트리거는 *주제*가 아니라 *발동 조건*으로 쓴다

| | 예 |
|---|---|
| **나쁨** | "스키마 마이그레이션을 작성·검증한다. **데이터베이스·쿼리·모델·영속성 작업에 사용.**" |
| **좋음** | "스키마 마이그레이션을 작성·검증한다. **마이그레이션을 추가·변경하거나 그 롤아웃을 검토할 때 사용.**" |

나쁜 쪽은 "인접한 모든 것"에 손을 든다. 트리거는 **언제 켜지는가**를 말해야지, **무엇에 관한 것인가**를 말하면 오발동한다.

### ② 트리거 예산은 공유 자원이다

카탈로그의 트리거는 한 공간을 나눠 쓴다. 스킬이 늘면 각 설명이 잘리거나 묽어져 **라우팅 품질이 전역적으로** 떨어진다. 즉 한 스킬의 장황한 설명은 *남의 스킬을 잠식한다.* 내 스킬 하나만 보고 "자세할수록 좋다"고 판단하면 공유지의 비극이 된다.

→ 스킬을 추가할 때 묻는다: **"이 설명이 다른 스킬의 발동을 방해하지 않는가? 서로 겹치는 트리거가 있는가?"**

### ③ 진입 문서는 문서가 아니라 라우터다

여러 갈래를 포함하는 스킬은 최상위 파일을 **얇은 라우터**로 둔다 — 어디에 무엇이 있는지 알려주되, **전부 읽으라고 요구하지 않는다.** 모놀리식 본문은 발동하는 순간 컨텍스트를 태우고 압축을 앞당긴다. 세부는 필요할 때만 열리는 하위 문서·스크립트로 민다. §4의 색인 원칙을 스킬 표면에 적용한 것이다.

## 8. 먼저 낡는 문장들

| 형태 | 깔려 있던 가정 | 지금 내는 비용 | 대체 |
|---|---|---|---|
| **무조건 사전 열람** — "수정 전 A·B·C를 모두 읽어라" | 스스로 필요한 문서를 못 고른다 | 오탈자 수정에도 전체 지도를 로드. 매 작업 고정 과금 | **조건부 포인터** — "서비스 경계는 A, 스키마 변경은 B, 배포 준비는 C" |
| **검증 독려** — "반드시 테스트하고 결과를 확인하라" | 확인 없이 완료를 선언한다 | 이미 하는 일을 또 시켜 **중복 실행**을 유발 | 삭제. 단 *비표준* 검증 요건은 남긴다 |
| **광범위 ask-first** — "변경 전 항상 물어라" | 시키지 않은 범위까지 넘본다 | 매 단계 승인 요청, 조기 종료 | §9 — 금지와 **사전 승인**을 함께 적는다 |
| **단계별 레시피** | 스스로 계획을 못 세운다 | 더 짧은 경로를 막음 | §3 — 불변식·수용 기준만 남김 |
| **exhaustive 미니 소스 트리** | 검색이 미덥지 않다 | 구조 변경 즉시 stale해지고 잘못된 위치를 선주입 | §4 — 디렉터리 색인 + 드문 landmark |
| **기능 snapshot** | 현재 상태를 못 읽는다 | 오늘의 UI·API를 장기 불변식으로 오인 | 코드·온디맨드 문서로 보냄 |
| **조상 재진술** | 자식이 부모를 못 받을 수 있다 | 모든 하위 작업의 비용과 의미 drift를 함께 늘림 | §5 — 로컬 delta만 |
| **금지 목록 누적** | 과거의 모든 실패가 재발할 수 있다 | 삭제된 과거까지 상시 컨텍스트로 운반 | 실패 모드와 함께 폐기 |

> ⚠️ **모든 조타가 낡는 건 아니다.** 위반 비용이 큰 운영 불변식(데이터 손실·배포·승인·권한 경계)은 모델이 아무리 좋아져도 남긴다. 모델은 *조직의 정책*을 추론할 수 없다. 낡는 것은 **능력을 보정하던 문장**이고, 남는 것은 **정책·경계를 선언하던 문장**이다. 이 구분이 감사의 핵심 축이다.

# 3부 — 경계·완료·이식성

## 9. 경계는 비대칭이다 — 금지만큼 허가도 적어라

경계 문장은 보통 "넘지 마라"만 적힌다. 넘었을 때의 비용은 사건으로 보이지만, **멈추지 않았어야 할 때 멈춘 비용은 보이지 않기** 때문이다. 능력이 오른 모델일수록 경계를 과잉 준수해서, 계속했으면 좋았을 지점에서 승인을 구하며 선다.

→ 경계 정의를 **양방향**으로 적는다.

```
<되돌릴 수 있고 영향이 격리된 작업 부류>는 단계마다 승인을 구하지 말고 끝까지 수행하라.
단 <경계 조건>에 닿으면 멈추고 보고하라.
```

**사전 승인(pre-authorization)의 자격 조건** — 셋을 모두 만족할 때만:

1. **가역성** — 되돌릴 수 있는가.
2. **격리** — 영향이 일회용·로컬 범위에 갇히는가(운영계·공유 상태·외부 서비스에 닿지 않는가).
3. **관측 가능성** — 잘못돼도 즉시 드러나는가.

하나라도 안 서면 게이트를 유지한다. 외부로 나가는 행위(발행·전송·배포), 되돌리기 어려운 삭제·덮어쓰기는 능력과 무관하게 승인 대상이다.

## 10. 완료 계약: '끝'을 정의하지 않으면 모델의 중단 성향이 대신 정한다

어디서 멈추느냐는 모델마다 다르다. 어떤 기준선은 한참을 혼자 달리고, 어떤 기준선은 일이 남았는데도 검토를 받으러 일찍 돌아온다. **이 성향에 기대는 요청은 기준선이 바뀌면 같이 깨진다.** 그러니 '끝'은 지침이 아니라 *요청*에서 못 박는다.

- **완료 조건을 먼저 정의한다** — 무엇이 참이면 끝인가.
- **작업에 포함되는 범위를 명시한다** — 실행·결과 확인·실패 수정·재확인까지가 일이라면 그렇게 적는다.
- **"1차 패스 후 검토받아라"류를 점검한다** — 조기 종료 편향을 만든다. 그 체크포인트가 정말 필요한지 확인하고, 아니면 뺀다.
- **탐색 작업은 범위와 정지점을 함께 준다** — "어디까지 파고, 무엇을 보면 멈춘다."

## 11. 이식성: 지침은 여러 모델·여러 사람이 읽는다

저장소의 지침은 작성자 한 사람의 설정만 조타하지 않는다. 다른 기준선을 쓰는 동료와 미래의 자신도 같은 문장을 받는다. **한 기준선의 약점을 보정하려고 넣은 문장이 다른 기준선을 과잉 제약한다.**

- **분리한다** — 모델 불변(경계·불변식·소유권·정책)은 상시 지침에, 모델 의존 보정은 최소로·**한시적임을 명시**해 격리한다.
- 보정 문장에는 **왜 넣었는지**를 남긴다. 이유가 없으면 다음 감사에서 지울지 말지 판단할 수 없다.

# 4부 — 감사

## 12. 감사

**모든 판정을 끌고 가는 질문 하나:**

> 각 문장에 묻는다 — **이건 능력을 보정하는 문장인가, 정책·경계를 선언하는 문장인가.**
> 정책·경계 선언은 능력과 무관하다: 유지한다. 능력 보정은 유효기간이 있다: 가정을 노출하고 아직 참인지 관측한다.

### 절차

1. **인벤토리** — 모든 지침, alias, root-to-leaf 상속 순서를 찾는다. 개별 크기가 아니라 **가장 긴 조립 경로**를 기준선으로 잡는다.
2. **분류** — 두 축을 동시에. 역할(`라우팅 / 고위험 불변식 / 자동 집행 후보 / 온디맨드 절차 / 역사`)과 시효(능력 보정 / 정책 선언).
3. **보존 게이트** — 남길 후보에 §2를 적용한다.
4. **가정 검증** — 능력 보정 문장마다 "모델이 무엇을 못한다는 가정인가"를 적고 **관측한다.** 문장을 빼고 대표 작업을 돌려 보는 것이 가장 싸다. 추측으로 지우지 않는다.
5. **트리거 감사** — §7: 주제가 아니라 발동 조건인지, 카탈로그 내 충돌이 없는지.
6. **대칭화** — §9: 금지만 있는 경계에 사전 승인을 채운다.
7. **이전 후 제거** — 상시 지침에서 빼지만 계속 필요한 규칙은 거처(자동화·문서·live metadata)를 먼저 만들고 실제 회수 또는 fail-fast를 확인한다.
8. **위에서 아래로 재작성** — leaf에는 차이만 남긴다. 현재 구현과 대조하되 구현 snapshot을 지침에 복사하지 않는다.
9. **조립 검증** — 대표 leaf의 첫 제목과 마지막 문장이 실제 모델 컨텍스트에 모두 보이는지, 관측 한도에 안전 여유가 있는지, alias가 같은 SSoT를 가리키는지 확인한다.
10. **제안 → 승인 → 적용** — 유지/이전/이동/삭제를 근거와 함께 올리고, 승인된 것만 반영한다.

### 정말 좋아졌는지 검증

조립 검증만으로 engineering 품질이 좋아졌다고 결론 내리면 안 된다. verbose / light / risk-weighted hybrid 조건에서 같은 대표 작업을 반복해 비교한다.

- 조립 토큰과 truncation 여부
- 올바른 owner·SSoT에 도달하기까지의 시간, 검색 호출, 읽은 범위
- task success와 첫 수정의 정확도
- 중대 제약 위반, 리뷰 지적, 재작업 횟수

지침 외 변수를 고정한다 — 모델, 상위 system/developer prompt, tool catalog, memory·retrieval 정책, reasoning 설정, sandbox, 검색·시간 예산. 그렇지 않으면 지침이 짧아진 효과와 다른 컨텍스트가 탐색을 늘린 효과를 구분할 수 없다. 실제 운영 조건을 재현하는 시험과 지침 자체를 분리 측정하는 통제 시험을 나눠 둔다.

**성공 기준:** task success와 중대 위반이 비열등하고, 각 비용 축의 악화가 사전 허용 범위 안에 있으면서 주입·탐색·재작업·유지보수의 **가중 총비용이 감소**하는가. 핵심 지표는 corpus 합계 하나가 아니라 최악의 조립 경로와 실제 작업 결과의 결합이다.

감사 자체를 모델에게 맡길 수 있다. **단, 판정이 아니라 후보 제안까지만** 맡긴다 — 자기 능력에 대한 자기 보고는 증거가 아니다.

## 13. 가드레일

1. **삭제 근거는 관측이지 평판이 아니다** — "요즘 모델은 잘한다더라"는 근거가 아니다. 빼 보고 확인한 것만 지운다.
2. **정책은 능력과 무관하다** — 위반 비용이 큰 경계·승인 게이트는 모델이 좋아져도 남긴다. 낡는 건 능력 보정뿐이다.
3. **이전 후 제거** — 규칙 폐기와 집행 위치 이동은 다른 판단이다. 메커니즘이 실제로 차단함을 확인한 뒤 문장을 지운다.
4. **한 번에 다 걷어내지 않는다** — 묶음으로 지우면 무엇이 회귀를 일으켰는지 알 수 없다. 부류별로 나눠 적용하고 측정한다.
5. **적게 쓰는 것은 결과일 뿐** — 목적은 토큰 절약이 아니라, 가장 구체적이고 중요한 경계가 필요할 때 실제로 모델에 도달하면서도 누락 비용을 키우지 않는 데 있다.
6. **인코딩과 삭제는 한 쌍** — 새 조타를 넣을 때마다 낡은 조타를 하나 찾는다(→ [수확 방법론 §2④](./compounding-engineering-learning-harvest.ko.md)).
